Schema — sem-view-more

Contract per conventions.md v0.5. This document records the one known usage of the element — a wrapper around a sem-embed on the landing page — and nothing more. It is authored directly as SemText; it has no Markdown twin yet, like embed.sem.html. Where the usage does not settle a question, the question is flagged open below, not answered.

Authoring form

<sem-view-more>
  <sem-embed data-source="./non-summary-file.semtext.html" data-section="#Anchor Name"></sem-embed>
</sem-view-more>

The element is a wrapper around a single sem-embed. The embed names the content: data-source is the referenced document (a non-summary file — the full version), data-section is the section within it (#Anchor Name). The wrapper marks that embedded section as an expandable summary view.

Known contract

  • sem-view-more wraps a sem-embed and marks the embedded section as an expandable summary view: the embedded section stands for the fuller content of the referenced document, and the wrapper marks it as something the reader can expand beyond the summary presentation.
  • The wrapper is authored around the embed; the example gives it no attributes and no other content. Nothing beyond that is established.
  • Machine (§8, provisional): registered record: false in semtext.schema.json — a transparent wrapper on the sem-source precedent — strictly because the usage shows nothing the wrapper itself contributes; see the open question below. The embed child's own contract (resolution, sanitisation, the extraction invariant) is embed.sem.html's and is unchanged by the wrapper as far as the usage shows.

Open questions

Open — attribute spelling: the known usage writes data-source/data-section — the v0.4 class-form data-* spellings — on a sem-embed tag-form element, where conventions §2 makes the bare spelling (source) canonical. Whether the canonical authoring form for this pairing is bare (source, section), data-*, or both accepted, is unresolved. Open — section selection: the specced sem-embed selection parameter is view — the id of one block — with a #fragment in source as sugar. The usage instead carries data-section="#Anchor Name", a value with a space that cannot be an element id and looks like a heading anchor label. Whether section is an alias of view, a separate heading-anchored selector, or a legacy spelling of the fragment sugar, is unresolved. Open — wrapper contract: the usage settles none of the wrapper's own semantics: whether sem-view-more accepts attributes (e.g. its own summary label), whether it may wrap anything besides a sem-embed, whether it requires exactly one embed child, how it behaves in each tier (CSS-only / fallback / upgraded, print), and whether it mints a record or is presentation-only chrome (the record: false registration above is the conservative default, not a decision). Each is unresolved. Schema — sem-embed: the wrapped element's resolution, security and extraction contract. Root spec — §2 attribute spellings, §8 the extraction invariant. Machine-readable schema.
