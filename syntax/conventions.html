0 · Model

One file, three consumers:

  • Human / browser — double-click the .html/.mhtml; current Chrome/Edge/Brave/Firefox/Safari render styled, interactive documents. No server, no build, no install.
  • LLM / non-visual — the same file read structurally; attributes qualify every datum; same XML vocabulary NPL's MCP server already speaks.
  • Terminal — browser render or DOM-text extraction; content complete without JS.

Element names are semantic (sem-fact, sem-detail) — what content is; presentation is parameterized (view-as="quiz|flashcards|list") — how it renders. NPL conventions live inside the tags, never as a pre-HTML grammar.

This page is the reference: every component class below is live. Try the embedded facts widget in §5.

1 · Document skeleton

<!doctype html>
<html lang="en" data-sem-theme="minimal-tech-light">
<head>
  <meta charset="utf-8">
  <title>…</title>
  <link rel="stylesheet" href="semtext/themes/minimal-tech-light.css">   <!-- folder form -->
  <style>/* inline core CSS — theme tokens + component base */</style>
  <script src="https://cdn.tailwindcss.com"></script>
  <style type="text/tailwindcss">/* @apply refinements on sem-* */</style>
  <script id="sem-fallback">/* always-embedded vanilla handler */</script>
  <script defer src="semtext/semtext.js"></script>   <!-- Lit upgrade, optional (later milestone) -->
</head>
<body>
<div class="sem-enhanced-document">
  <div class="sem-agent">
    <div class="sem-agent-name">…</div>
    <div class="sem-agent-bio">…</div>
    <div class="sem-agent-instructions">…</div>
  </div>
  <!-- content -->
</div>
</body>
</html>
  • .sem-enhanced-document is the required root wrapper in v0.4.
  • Metadata children (.sem-agent, future .sem-org, .sem-context) are bare semantic blocks — machine-facing, lightly styled. ❓Q1 keep bare vs sem--prefix everything inside?
  • Ordinary semantic HTML is always valid content; sem-* enhances where interactivity pays.

v0.4: identity = class, parameters = data-* attributes. Global set (any .sem-* element):

data-view-as is the core inversion: a fact is a fact in every view; the attribute only selects rendering. Unknown value ⇒ falls back to list/plain.

3 · NPL notation inside tags

Compact notation is legal inside element text where the schema allows; attributes are canonical, notation is sugar:

NotationMeaningWhere
span.sem-highlightrecall target — occludes in quiz/flashcard views, <em>-equivalent in plain viewany prose element
[[cloze]]inline occlusion sugar (≡ highlight)sem-detail, sem-fact
term :: valuepairsem-property text, fact compact form
✅ … / ✗ …correct / distractorquiz options sugar
→ …currentsem-step status sugar
[hint | reveal]agent-facing instruction, human-rendered hintinstruction-bearing elements ❓Q2

Structured children (.sem-statement/.sem-conclusion) always win over the :: compact form when both present.

4 · Fallback handler & degradation rules

  • <script id="sem-fallback"> is embedded inline in every portable doc (~2–4KB vanilla JS): data-view-as switching, reveal toggles, highlight occlusion, basic quiz checking, theme picker. Zero external resources required for full baseline interactivity.
  • semtext/semtext.js (Lit 3, IIFE) upgrades elements in place when reachable; component implementations supersede fallback behaviors. Handoff contract: fallback sets data-sem-fallback; components remove it on upgrade. BDD asserts both tiers + the handoff.
  • Core CSS (inline, plain) keeps the page presentable with JS and CDN absent; Tailwind refinement is a progressive enhancement layer.
  • Content lives in light DOM (searchable, copyable); interactive chrome may use shadow DOM once Lit lands.

5 · Element entries

sem-note — callout

<div class="sem-note" data-variant="warning">
  JWTs must rotate <strong>per session</strong>.
</div>

Variants info (default) warning tip danger; collapsed attr hides .sem-note-body behind a generated summary. Light DOM, content searchable.

sem-fact — atomic assertable pair

<div class="sem-fact" id="f-jwt" data-kind="concept">
  <div class="sem-statement">JWTs rotate per session</div>
  <div class="sem-conclusion">Short-lived access; refresh grants a new pair.</div>
</div>

Compact form: term :: conclusion as direct text. Machine view: statement+conclusion = structured assertion.

sem-facts — collection; the flagship surface

Normative: syntax/schema/sem-facts.md.

<div class="sem-facts" data-view-as="quiz" data-controls="shuffle">
  <div class="sem-fact">…</div>
  <div class="sem-fact">
    <div class="sem-conclusion">true answer</div>
    <div class="sem-distractor">decoy</div>
  </div>
</div>
  • list (default): all facts visible; filter/tags later.
  • flashcards: front = statement, back = conclusion; flip click/Space; ←/→; progress.
  • quiz: statement shown; options = explicit .sem-distractor children else sibling conclusions; scoring.

sem-detail / sem-details — prose with occludable content

Normative: syntax/schema/sem-details.md.

<div class="sem-details" data-view-as="quiz">
  <div class="sem-detail">
    The OIDC token travels in the <span class="sem-highlight">Authorization</span> header.
  </div>
</div>

Plain view: highlight renders emphasized. Quiz view: occluded, reveal per span. Live: refresh tokens never reach the browser (this page is in plain mode — swap data-view-as to see occlusion).

sem-procedure / sem-step — ordered, status-annotated procedure

<div class="sem-procedure" data-kind="runbook" role="list">
  <div class="sem-step" role="listitem" data-status="done">provision Infisical path</div>
  <div class="sem-step" role="listitem" data-status="current">port-forward MinIO</div>
  <div class="sem-step" role="listitem">run migrations</div>
  <div class="sem-step" role="listitem" data-status="blocked">cut release</div>
</div>

data-status: done current todo (default) blocked. DOM order = execution order (ordinals positional); ✅/→/❌ sugar is display-only — the attribute is canonical. Zero-JS element. Normative: syntax/schema/sem-procedure.md.

sem-properties / sem-property — definition block

<div class="sem-properties" data-kind="config">
  <div class="sem-property" data-key="token ttl"
       role="definition" aria-label="token ttl">15m</div>
</div>

data-key = term, text = value; key column renders via CSS attr(); role="definition" + aria-label carry the pair to AT. term :: value sugar is display-only. Q2 resolved: pure <dl> v1, no chrome. Normative: syntax/schema/sem-properties.md.

sem-views / sem-view — switchable perspectives

<div class="sem-views" id="deploy">
  <div class="sem-view" data-name="Helm" data-active role="tabpanel">…</div>
  <div class="sem-view" data-name="ArgoCD" role="tabpanel">…</div>
</div>

data-name unique per container; data-active marks the initial view (first wins if absent). Fallback builds the tab bar, manages arrow keys and deep-links (#id/name), fires sem-navigate {id,name,index}. JS-off: all views stacked. Q3 resolved: sem-views. Normative: syntax/schema/sem-views.md.

Each view is the same subject under a named perspective — deep-link form #spec-views/quiz style.
This tab bar, keyboard roving focus, and hash sync are the v0.4 fallback handler executing the spec.

sem-reveal — Q→A disclosure

<div class="sem-reveal" data-summary="Why not localStorage?" collapsed>
  Tokens in localStorage are readable by any script on the page…
</div>

data-summary optional — first body line (≤60 chars) derives it; collapsed starts hidden, otherwise open. Fallback wraps in native <details>; JS-off: fully visible. Non-assertive counterpart to the sem-fact Q/A shape. Normative: syntax/schema/sem-reveal.md.

Intent: a note is an annotation (variant tone); a reveal is exposition (Q→A). Same mechanism, different semantics — machines distinguish them.

sem-progress — completion meter

<div class="sem-progress" data-value="0.62" data-label="coverage"
     role="meter" aria-valuemin="0" aria-valuemax="1" aria-valuenow="0.62"></div>

data-value canonical 0..1 (render clamps, attr untouched); data-label default progress; fallback renders track + fill + label :: N%; JS-off: text-only via CSS attr(). data-status="done" ⇔ 1 by convention. Normative: syntax/schema/sem-progress.md.

6 · Theme conventions

  • data-sem-theme="<slug>" on <html>; one theme per doc; tokens on [data-sem-theme] (this page uses them live).
  • Compiled themes from TRP-format YAML → semtext/themes/<slug>.css; --sem-* tokens; :not(:defined) vocabulary base when custom elements land.
  • Ship 4 TRP ports: minimal-tech-light (default), nocturne-console, organic-warm, editorial-settings; auto light/dark via prefers-color-scheme, data-color-mode forces.

7 · Distribution forms

  1. Folder — doc.html + relative semtext/ (IIFE semtext.js + themes/).
  2. Single-file — fallback + CSS + (later) Lit bundle + data all inlined; one file shares anywhere.
  3. MHTML — multi-page bundle.

Hard rules: no ES-module scripts; no runtime fetch in portable docs; the fallback handler is always embedded regardless of form.

8 · Machine-readability contract

  • Semantic children (.sem-statement, .sem-conclusion, .sem-highlight) + data-* attributes qualify every datum.
  • Well-formed, correctly nested HTML — parseable by XML/HTML tooling; same vocabulary is the XML variant of NPL (§9).
  • Behaviors + attributes documented per schema = agent integration surface.
  • A "text extraction" reference recipe (DOM → annotated plain text) ships with the lib.

9 · NPL XML-variant alignment

This vocabulary is the XML variant of NPL: NPL yaml already models agents (name/bio/instructions), instructions, and structured prompt sections via the MCP server; this format is its document-shaped rendering target. Alignment tasks (tracked, not blocking): map .sem-agent children to NPL agent schema; map facts to NPL knowledge records; define sem-enhanced-document as a valid MCP render target. ❓Q4 mapping ownership.
